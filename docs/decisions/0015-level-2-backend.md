# 0015 Level 2 through the runner

Level 2 rows run through the box's runner. The backend `backend::level2::Level2` wraps `ignorarium_guest::host::run_row` (0010), so each row runs in one fresh Cloud Hypervisor machine. The guest crate still knows nothing of the box.

Decision:

- Configuration: three environment variables name the host files. `IGNORARIUM_VM_VMM` is Cloud Hypervisor, `IGNORARIUM_VM_KERNEL` is the guest kernel, and `IGNORARIUM_VM_AGENT` is a static build of the `ignorarium-guest` binary, the guest's `/init`. `machine.toml` holds spend caps, not paths.
- Probe: level 2 is unavailable when `/dev/kvm` does not open for reading and writing (missing, or the user is not in the `kvm` group), a variable is unset, the hypervisor has no execute bit or does not match its pin, the kernel does not match its pin, the agent names a program interpreter (it is not static), or `mkfs.ext4` or `debugfs` cannot run. The probe lists every fault it finds, joined by `; `, so one `ignorarium probe` shows all that is missing. The pins are those of 0010: "v54 or later" means exactly the pinned v54.0 until the pin moves.
- Launcher: the first line of `<vmm> --version` when it starts with `cloud-hypervisor v`, else `cloud-hypervisor unknown`. The box records it as at level 1, in the `run.start` event and in every row record. Beside it goes `agent_sha256`, the hex SHA-256 of the agent bytes the rows boot. The backend reads the agent once, with the initramfs, so the hash names the bytes every row boots, even when the file changes later.
- Disks, four per machine:
  - rootfs: the environment root as a read-only ext4 disk at `<root>.ext4`. `prepare` builds it, or finds it, when level 2 is a candidate, so a row builds it only when it has gone since. The store publishes a root once and never changes it, so the disk never goes stale. The build writes a temp file and renames it, so a failed build leaves nothing.
  - A root keeps the image's file modes, and mkfs.ext4 copies each file as the box's user. A file that user cannot read (mode 0000, say) stops the build, so `prepare` looks for one first. One makes level 2 unavailable for that study: `prepare` chooses a lower level with a `run.isolation` event, or refuses at `min_isolation = 2`, both with `level 2 cannot build the disk of environment <digest>: <path> has mode <mode>, so mkfs.ext4 cannot read it`. It is never a fault retried on each row, and the box never changes a mode in the store. A build that fails for a fault of the host refuses the run.
  - input: the row's sealed input view, read-only, built per row.
  - payload: the payload's folder, read-only, built per row. The guest mounts it at `/payload`.
  - output: a raw zero-filled file, per row.
  - The initramfs is built from the agent's bytes on first use, once per backend, and written into each row's scratch folder, `<temp>/ignorarium-vm-<pid>-<n>` (mode 0700). The folder goes when the row ends.
  - Cloud Hypervisor v54 splits an option at a comma and fails to parse one that holds `[`, `]` or `"`. A kernel, initramfs, rootfs, serial log or scratch path that holds one of the four is refused before the VMM starts, an infrastructure fault that names the path and the character. An `=` or a space parses.
- Disk roots hold exactly their folder. mke2fs always makes `lost+found` (mode 0700, owned by root), which the guest's user cannot read, so the box removes it with debugfs (e2fsprogs, a level 2 host tool): `debugfs -w -R "rmdir lost+found"`, unless the folder has its own. debugfs exits 0 when a request fails, so any line on its error output but its version banner fails the build. A top-level `lost+found` that is not a folder, in the input view or the payload folder, is refused at prepare time as an input fault, with no retry: `level 2 cannot make a disk of the input view: lost+found at its top is not a folder, and ext4 keeps that name for one; rename it`.
- Payload paths: `argv[0]` becomes `/payload/<file name>`, as at level 1. The guest's unprivileged user runs it, so it needs other-execute. The payload gets `IGNORARIUM_IN=/in`, `IGNORARIUM_OUT=/out`, the job's own variables and `IGNORARIUM_SEED`. It starts in `/out` at levels 1 and 2.
- Exit: exit code 0 is a success, any other code is a payload result, and a signal `s` is code `128 + s`. A payload that exits 0 and leaves outputs the pack refuses voids the row: `cannot pack output: <why>`, with the guest's text capped at 200 characters, quoted and escaped, as the host shows all guest text. An output path past `PATH_MAX`, which a payload can make with calls relative to a folder, is such a refusal, as levels 0 and 1 void a row whose outputs they cannot hash. The host makes each entry relative to the output folder, so that folder's own path does not count. The output hash and links are kept only for a success or a payload result whose outputs packed. Without a report (a failed boot, a guest error, a missed deadline, a hash mismatch, a host I/O error) the row is an infrastructure fault with the host's message, retried as any such fault. So is a report no guest can mean: CPU time outside 0 to wall time × vCPUs, an exit code outside 0 to 255, or a signal outside 1 to 127.
- Wall time: the agent ends the payload at the row's wall timeout. The row is then a payload result, code 124, with its outputs hashed, as at levels 0 and 1. The host's deadline is the job send plus the wall timeout plus 30 s. Past it, the host kills the machine and the row is an infrastructure fault. Disk building and the boot sit outside the payload's wall time and inside the row's `wall_seconds`.
- Stop and timeout: the VMM leads its own process group (`setpgid`). `Watch::started` names that group once per row, and the runner writes it to the run's `row.json` with its start time, so a later run can kill it when the box died mid-row. Every way out (a stop, a missed deadline, an error, a drop) kills the group with SIGKILL, then reaps the leader. Until the reap, the leader's pid names the group, so no other group can take that id. The host sees the VMM exit with a `waitid` that leaves it unreaped (`WNOWAIT`), so the box keeps SIGCHLD at its default action. The host calls `Watch::tick` between the disk steps and every 5 ms while it waits on the VMM or the guest, frames in flight included, so the runner's heartbeat and stop checks run during a long row. A stop ends the row as `Exit::Stopped`, as at levels 0 and 1.
- Self-test: before the self-test, the agent writes `2` to `/proc/sys/kernel/io_uring_disabled`, so `io_uring_setup` fails with `EPERM` for every guest process, root included. The guest self-test checks that `lo` is the only interface, that a route lookup to a documentation address finds no route, that a second connect to the host's control port fails, and that `io_uring_setup` fails. The box maps the result onto level 1's record, so the `sandbox.selftest` event and its readers stay as they are: `connect_blocked` is loopback only and no route, `vsock_blocked` is no host path, io_uring is denied, absent or open by level 1's rule, and `vsock_absent` is false. A failed self-test never runs the payload. The row is an infrastructure fault, `guest self-test failed: <names> was not blocked`, with the names joined by " and ", as level 1 words it.
- CPU: the row's `cpu_seconds` is the payload CPU the guest reports. Without a report, the CPU is unknown (`the guest sent no report, so the payload's CPU time is unknown`), except when the box refused the row before the VMM started, the boot failed, or the box stopped the row. `Backend::cpus` is the vCPU count, so a row the box ended is charged wall time × vCPUs. The VMM's own CPU, its boot and its threads, is not in the row's `cpu_seconds`. The host reaps the VMM with `wait4`, which reads that CPU, on every way out, and the row's outcome carries it as the box's spend. The host meter, and so the `cpu_hours` cap, counts it, and the row and spend records hold it as `box_cpu_seconds`, so a resumed run and `ignorarium status` count it too.
- Output links are data at every level. A link's row is `[path, "link", <SHA-256 of the target bytes>]`. One row function in `ignorarium_guest::tree` serves the agent, the level 2 host and levels 0 and 1; the static agent cannot depend on the box, so the function lives in the guest crate. The pack carries any link target but an empty one, one with a NUL, or one of 4096 bytes or more. `unpack` records each link's path and target and never makes the link, so nothing on the host can follow it. `pack::write` and `pack::unpack` both hash the stream as it passes, each file's digest from the bytes as they are copied, so each output file is read once on each side. The row's outcome carries the link rows, and the `values.json` check hashes the output folder with them; a `values.json` that is a link is not a regular file, as at levels 0 and 1. Hashes of trees without links did not change. At levels 0 and 1, a tree with links now hashes its targets, and an output folder that is a link voids the row with `cannot hash output: top dir is a link`.
- Machine size per row, as fields of `Level2`: 1 vCPU, 1024 MiB of memory, a 256 MiB output disk, 30 s from the VMM start to the guest's first message, 10 s for the VMM to exit after the report, and 30 s of report slack.
- `/out` caps: the tmpfs gets `size` = half the output disk and `nr_inodes` = that half divided by the most one pack entry costs besides file data (12,296 bytes: the 4 KiB entry charge, plus the longest path and the longest link target with their headers). With the default disk that is 128 MiB and 10,915 inodes. A full `/out` then always fits the pack. A payload that fills `/out` gets `ENOSPC`, its own result, never a retried infrastructure fault. A sparse file or hard links take less of `/out` than of the pack and can still go over; the pack then refuses them, as above.
- No environment, no level 2: level 2 runs rows only in the study's environment image. `prepare` chooses the backend among those whose probe finds them available now and that meet `min_isolation`: a host can run level 2 and not level 1, so the candidates are not every level up to the highest. For a study with no `env/` and no `pins.environment`, levels 2 and up drop out and the highest lower level runs. One `run.isolation` warning event names the level, the levels skipped and why: `{"level": 1, "skipped": [2], "reason": "level 2 runs rows in the study's environment image; the study has no env/ and no pins.environment"}`. When no level is left (`min_isolation = 2`), `prepare` refuses before any row: `environment: level 2 runs rows in the study's environment image; add env/ or set pins.environment`. This is selection at prepare time from what the study holds, not a fallback after a failure, so 0008's rule holds: the box never falls back to a lower level by itself.
- Host paths in records: a backend's message can name host files, such as the VMM path, the `vmm.log` tail, or the text of bubblewrap, `mkfs.ext4` and `debugfs`. The runner redacts it at one point, where the backend's message returns, before any spend record, row record, event or pause takes it. The probe's reason for a pause goes through the same redaction. The study root, the box home and the user's home become `<root>`, `<home>` and `~`, each in its given, absolute and canonical spelling, longest first, so a folder inside another is replaced whole. Only absolute spellings count, and never `/`.

Measured through the runner (one cloud host with 6 vCPUs and nested virtualization; level 1 is bubblewrap 0.11.1; the box's test payload, a shell script that writes two small files; 11 trials, the first dropped because it builds the rootfs disk; the level order alternates by trial; 4 rows per study, the first dropped; 30 rows per level; ± is the 95% Student t half-width over the 10 trial means):

| Series | Mean |
|---|---|
| Level 1 row (`wall_seconds`) | 27.37 ± 0.91 ms |
| Level 2 row (`wall_seconds`) | 356.38 ± 6.11 ms |
| Level 2 boot (VMM start to the guest's first message) | 291.34 ± 6.82 ms |
| Level 2 row minus level 1 row, per trial | 329.02 ± 6.02 ms |

A level 2 row costs about 0.33 s more than a level 1 row; the boot is about 0.29 s of it.

Limits:

- The content store does not hold the image parts yet, and input disks are not cached by tree hash (issue #32). The rootfs disk is kept beside its root; the input and payload disks are built for every row.
- An image with a file its owner cannot read, such as the Fedora family's `/etc/shadow` at mode 0000, runs at level 1 only until the rootfs disk is built from the image's layers, which carry the modes (issue #32).
- `/tmp` exists only at level 2; level 1 has none (0008).
- Outputs are capped at half the output disk, 128 MiB and 10,915 inodes by default. Levels 0 and 1 have no cap.
- A process the payload leaves running is killed when the payload ends, and its CPU is not counted, as at levels 0 and 1.
- An output file its owner cannot read (mode 0000, say) hashes at level 2, because the agent reads `/out` as root. At levels 0 and 1 the box cannot read it and voids the row.
- The probe checks files and tools; it does not boot a test machine. A kernel or agent that passes the checks but cannot boot shows at the first row, as an infrastructure fault.
- A box killed mid-row leaves its scratch folder in the temp folder. A later level 2 row of the same user removes it once no process has that pid.
- The redaction replaces text, not path parts: with a home of `/a/b`, `/a/bc` becomes `<home>c`. A path outside the three folders, such as a `TMPDIR` under `/tmp`, stays as it is.

Why:

- One backend over `host::run_row` keeps the guest crate free of the box, so the crate can be tested and lifted alone.
- One row function at every level gives the same outputs the same hash at levels 1 and 2, links included. Hashing a link's target tells apart two outputs that differ only in where a link points.
- A process group that the runner records is the one handle that kills a VMM, and every process it started, after the box itself died.
- Capping `/out` in bytes and in entries keeps a payload's own excess a payload result: the pack can always carry what `/out` holds.
- The box records only checks that ran: the guest calls `io_uring_setup` itself instead of the box assuming the call is blocked.
- Choosing the level at prepare time keeps it a function of the study and the machine, fixed before any row and named in an event. Building the rootfs disk there finds an image that cannot become a disk once, not on every row.
